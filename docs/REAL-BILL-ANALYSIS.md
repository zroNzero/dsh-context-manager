# 真实账单分析（2026-11-11）—— 为什么「降幅 ≥50%」在当前口径下达不到

> 本文所有金额都来自 **provider 回传的 usage × 官方人民币单价**，没有任何估算。
> 复现命令见文末。结论与 `docs/STARTUP-PROMPT-v2.md` 的 Gate 1 直接冲突，需要重新定标。

---

## 1. 数据来源与两个必须纠正的口径

真实 usage 存在会话日志的 `assistant/message.data.usage` 里：

```json
{ "inputTokens": 760, "outputTokens": 1245, "cacheReadTokens": 117248, "cacheWriteTokens": 0, "totalTokens": 119253 }
```

**坑 1：`cacheReadTokens` 是会话累计值，不是单次值。**
它单调递增（实测 113/113、670/685 步递增）。整段求和会把账单虚增一个数量级
（一次错误口径下，某会话从 ¥13.16 被算成 ¥19.66，命中率从 10.6% 被算成 97.6%）。
单次缓存命中必须取**差分**：`hit_i = cacheReadTokens_i − cacheReadTokens_{i-1}`。

**坑 2：token 降幅 ≠ 账单降幅。**
官方单价（`src/modules/pricing.ts`，元/百万 token，flash 空闲档）：

| | 命中 hit | 未命中 miss | 输出 output |
|---|---:|---:|---:|
| flash 空闲 | 0.02 | 1 | 4 |
| flash 高峰 | 0.04 | 2 | 8 |

输出 token 单价是 miss 的 **4 倍**、hit 的 **200 倍**。
所以「工具密集会话 prompt 从 28,338 降到 6,848（−75%）」这种 token 口径的数字，
换算成人民币后可能只有个位数百分比。前半程的 45%–55% 结论正是踩了这个坑。

### 核心结论

> **把每一个请求的 prompt（含全部工具输出、工具 schema、历史消息）整体清零，
> 账单也只能降 44.2%。**

因为剩下的 **55.8% 是输出 token**，而 prompt 侧的任何压缩技术都动不到它。
`44.2% < 50%`，所以 Gate 1「真实账单降幅 ≥50%」**在现有单价表与现有杠杆下不可达**，
这不是调参问题，是算术问题。

## 3. 那 44.2% 里，钱到底花在哪

prompt 侧成本几乎全部来自 **miss（未命中缓存）**：

- miss 13.61M token ≈ ¥13.6（占全机器账单 35.4%）
- hit 6.36M token ≈ ¥0.13（占 0.3%）

也就是说，**prompt 的钱基本不是「内容太大」，而是「同样的内容反复以 miss 价重读」**。
命中率只要从 31.8% 抬到接近 1，prompt 成本就从 ¥13.7 掉到约 ¥0.4。

这是当前最大的单一杠杆，但它不是压缩：
- **前缀稳定性**（工具集/历史重写一旦变化，整段缓存在 provider 侧作废）；
- **TTL Keepalive**（武器 30，provider 缓存约 4 分钟过期，跨轮空闲后首请求必然全 miss）。

实测佐证：`dsh-mobile` 会话内，轮内（转轮之间的连续 step）命中率只有 24.2%，
轮首发请求 3.6% ——轮内本应接近 100%（上下文只追加），说明前缀在轮内被反复打断。

## 4. 对项目路线的直接影响

1. **Gate 1 必须重新定标。** 可选：
   - (A) 目标改为「prompt 侧成本降幅 ≥ X%」，X 取 44.2% 以内的可辩护值（建议 30%–35%）；
   - (B) 若坚持账单 ≥50%，必须引入**输出侧**杠杆（缩短 reasoning / 简单步骤降 effort /
     模型路由），而这是「降智」风险区，需要单独的质量门来兜；
   - (C) 承认物理极限，把 44.2% 写进验收文件，按 (A) 交付。
2. **优先级反转。** 继续堆压缩算法（TOON/CMW/CWL…）的边际收益受 prompt 上限约束；
   先把命中率从 31.8% 做上去，收益是压缩的数十倍。
3. **本轮已交付的地基**：真实账本（`src/modules/billing.ts`）已从 provider 的
   `StreamChunk.usage` 取数，拒绝在缺 usage 时用估算补齐；`real-bill.md` /
   `savings.json.realBill` / `costkiller_status` 均可查（自测 18/18、verify 22/22）。

## 5. 缓存损坏的账：轮内 vs 跨轮（2026-11-11 追加实测）

把全部真实请求按「是否回合首个请求」切开，就能看出两种性质完全不同的损失：

| 类别 | 请求数 | prompt token | 命中率 | 花费 |
|---|---:|---:|---:|---:|
| 回合首个请求 | 178 | 6,181,815 | 4.5% | ¥9.9153 |
| 轮内请求 | 5,511 | 14,849,260 | 42.0% | ¥30.1195 |

- **轮内 miss 占全部 miss 的 59.3%**（¥8.43，账单的 21.1%）。轮内上下文只追加，
  本来应该几乎全程命中——这部分是**前缀被打断**造成的纯损失，可以被「前缀修复」拿回来。
- **跨轮 miss 占 40.7%**（¥5.79，账单的 14.5%）。这是用户读回答期间缓存过期，
  只能靠 **TTL Keepalive** 拿回来，且只在用户于保活窗口内回来时有效。

两项合计上限约 **35.6%**（低于 44.2% 的理论 prompt 上限，因为命中本身也要钱），
这就是「不降智」前提下可辩护的收益空间。

### 5.1 用真实会话回放验证「重写是否真的破坏前缀」

`tools/prefix-replay.mjs` 把真实会话 `b82b2558`（686 个请求、1627 条消息）的消息面
按顺序重放，比较「上一次已发出的前缀」在这次请求里被改写了多少：

| 策略 | 前缀被改写的请求数 | 改动字符占比 |
|---|---:|---:|
| 旧策略（截断上限随实时 token 数漂移） | **473 / 686** | 1.0% |
| 新策略（上限固定） | 547 / 686 | 1.4% |
| **关闭重写** | **0 / 686** | **0%** |

关键结论：**只要保留「最近 N 条不动、更早的截断」这个结构，就一定会不断有消息
"越界"而被追溯改写**——固定上限只让每条的改写结果稳定，挡不住越界本身。
只有彻底关闭才能得到 0 改写。所以 `rewriteEnabled` 默认必须是 false，
把它当成「用户显式选择的、接受缓存损失」的压缩选项。

## 6. 据此做出的改动（2026-11-11）

定位到的根因：**历史重写的压缩上限是按「当前实时 token 数」算出来的**。
上下文每长一点，同一条旧消息就被截成另一个长度，于是已经发出去的前缀每次请求都变，
provider 只能从头 miss 重算。实测轮内命中率 24.2%（轮内上下文只追加，本应接近 100%）。

改了三处，并按第 5 节的实测追加两处：

| 改动 | 理由 |
|---|---|
| `rewriteEnabled` 默认 **false** | 截断旧内容省下的是 hit 价 token（¥0.02/M），作废前缀要按 miss 价（¥1/M）重算，净亏；且截断本身是信息损失 |
| 重写预算**固定**（不再传实时 budget） | 即使显式开启，也保证「同一段内容永远重写成同一段文本」；`rewriteHistory` 回调签名已移除预算参数，防止回归 |
| `semanticCacheEnabled` 默认 **false** | 相似度复用会在连续两次「继续」时让模型不被调用、重放上一轮回答，属降智 |
| `toolAttentionEnabled` 默认 **false** | 工具表在 prompt 最前面，按意图桶每轮重选会让整段缓存作废；它省下的 schema token 只有 hit 价，量级差 50 倍。工具目录仍回填，`search_tools` 照常可用 |
| **TTL Keepalive**（默认开，`keepaliveEnabled`） | 轮内与跨轮两种损失中，跨轮那 14.5% 只能靠「过期前用逐字节相同的前缀重放一次」拿回来；最多续 4 次、真实请求一到即取消 |

验收口径相应改为：**在不降智的前提下尽可能降本**，真实降幅以
`savings.json.realBill.reduction`（provider usage × 官方单价）为准，
理论上限 44.2%、可及上限约 35.6% 写死在 `docs/REAL-BILL-ANALYSIS.md` 里，
不允许再出现 token 口径的「降幅」。

### 下一步

1. **实测**：需要重启宿主让新 `dist` 生效，然后对比 `savings.json.realBill`
   的 `reduction` / `cacheHitRate` / `byPurpose['cache-keepalive']`，确认这三项改动

## 9. 输出侧：钱在哪（2026-11-11 实测后追加）

放开输出侧之后，先把「输出里面是什么」量清楚（同一会话 353 个 assistant 步骤）：

| 组成 | 占输出字符 | 说明 |
|---|---:|---|
| **reasoning** | **60.7%** | 思考过程，按 output 价计费 |
| tool-call 参数 | 37.6% | 真正写代码/diff 的部分 |
| 正文 | 1.8% | 几乎没有客套 |

而 output 占账单 67.1%，所以 **reasoning 一项约等于账单的 40%**。

再按「规划步 / 执行步」拆（规划步 = 本轮首个请求，最后一条消息是用户消息）：

| 步骤类型 | 步数 | reasoning 占比 | output 占比 |
|---|---:|---:|---:|
| 规划步 | 9 | 6.6% | 4.1% |
| **执行步** | **376** | **93.4%** | **95.9%** |

也就是说：**几乎所有思考开销都发生在「照计划执行」的步骤上**，而 profile 把每一步都钉在
`max`（模型自己的说明：max = "Reserve for the hardest quality-first tasks"，
high 才是 "the default balance for most tasks"）。

对应实现 `src/modules/effort-policy.ts`：

- 按本轮用户消息判定档位（trivial / easy / normal / hard）；
- **规划步**拿该档位的完整思考预算；
- **执行步降一档**（max→high、high→low），因为计划已经有了，重推一遍是纯开销；
- 工具报错时**回升到 hard 档**（诊断需要深度）；
- 硬安全阀：`lowerEffort()` 保证**只降不升**，宿主若已更低就听宿主的；
- 每次决策写 `effort.decided`（tier / from / to / reason / effortSource），可逐条审计。

预估（**预测**）：若 max→high 能让执行步的 reasoning 降 30%–40%，
则 ≈ 0.934 × 0.35 × 0.607 × 0.671 ≈ **13% 账单**；再叠加简单轮次的 low/off。

## 10. 宿主契约：prepared call 的配置在 dispatch 前不可变（2026-11-11 事故）

第一次上线动态 effort 时整轮全部失败，宿主报：

```
INVALID_PREPARED_CALL: prepared LLM call config changed before adapter dispatch
```

原因是 DSH 的 `prepareCall` 会**冻结** `LlmCallConfig`（provider / model /
reasoningEffort / temperature / maxTokens / stop），dispatch 前严格比较；
而我们在 `llm.stream` 阶段才改 `reasoningEffort`，两边必然不一致。
折叠只改 messages/tools，不在比较字段里，所以不是它。

正确做法是宿主自己的 `ConfigureCall` 钩子（`prepareCall(config, signal, configure)`
的第三个参数）：它返回的 controls 会被冻结成最终配置，dispatch 时自然一致。
本插件的实现：

- `configureControls` 与宿主传入的 configure **组合**（宿主先选，我们再只下调）；
- `llm.stream` 直连路径仍然改 options（那里不存在 prepared 配置）；
- 保活**不能**复用 `prepared.stream`：它是单次可派发句柄，第二次派发会抛
  `LlmError: a prepared LLM call can only be dispatched once`（实盘踩到过）。
  保活改为通过宿主原始的 `llm.stream` 自己开一次 `maxTokens=1` 的调用；
- 保活加了每会话两次失败的熔断，避免宿主行为变化后持续烧钱。

回归测试 `prepared path: effort frozen before dispatch, keepalive opens its own call`
用假宿主复刻了这条校验：故意传不一致的 effort 必须被拒绝，否则断言本身无意义。

### 早期实测（样本小，非受控）

| 窗口 | 请求数 | 平均 output | p50 | p90 |
|---|---:|---:|---:|---:|
| 策略生效前（全程 max） | 392 | 615 | 296 | 1668 |
| 策略生效后 | 64 | 508 | 328 | 1228 |

长尾缩短明显（p90 −26%），均值 −17%，中位数基本持平——符合「省掉的是过度思考，
不是正常作答」的预期。样本量小且任务构成不同，**还不能当作结论**。

## 11. 配对校准：reasoning effort 的真实折算率（2026-11-11 实测）

先前所有 effort 相关的数字都只能是区间，因为缺一个东西：**同一 prompt 在不同档位下
到底差多少 output token**。用一次性仪器补上了（`src/modules/calibrate.ts`，
状态目录放 `calibrate.flag` 即在下一次 apply 后自动跑一次，跑完删 flag）。

3 条 prompt（调试类 / 推理类 / 概念类）× 4 档，串行真实调用（延迟 1.3–5.6s，不是缓存）：

| effort | 平均 output | 平均 reasoning 字符 | 相对 max |
|---|---:|---:|---:|
| max | **608** | 1808 | — |
| high | **344** | 967 | **−43.4%** |
| low | 357 | 851 | −41.3% |
| off | 96 | 0 | −84.3% |

**关键结论**：悬崖在 `max → high`（−43%），而 `high → low` 几乎不省钱（344 vs 357）。
所以：

1. profile 长期用 `max` 是纯浪费；
2. 真正干活的步骤**不该**掉到 `low` —— 花一样的钱、少一半思考。执行步现在兜底在 `high`；
3. 只有 `trivial`（机械任务：格式化/翻译/改名…）才降到 `off`，那里才是真省（96 vs 608）。
   `easy` 的判据只是「用户消息短」，而短消息往往最含糊，执行步现在也用 `high` 兜底。

### 换算到账单

- 真实流量 reasoning 占输出字符 **60.7%**；max→high 砍掉 reasoning **46.5%**
  → 输出降 ≈ **28%**（tool-call 参数那 37.6% 不缩）。
- 执行步承载 **93.4%** 的 reasoning → 全流量输出降 ≈ **26%**。
- 输出占账单 41%–67% → **effort 杠杆 = 11%–18% 账单**。

### 校准踩到的两个坑（都已修）

1. **精确响应缓存的 key 不含采样参数**：四档拿到完全相同的 output、11/12 次耗时 1–4ms。
   现在 `reasoningEffort / maxTokens / temperature / stop` 都进 key；校准 prompt 另加 nonce。
2. **热重载会层层套娃**：宿主 in-place 重新应用不 dispose 旧实例（两次 reload 之间没有任何
   `apply.dispose`），旧层缓存会先拦截新层调用。现在用 `globalThis` 单例先拆旧层再装，
   disposer 幂等。

## 14. 两个把降幅记账归零的缺陷（2026-11-11 已修）

**缺陷 1：effort 记账带 5 秒过期。**

```ts
effortContext: () => lastEffort && Date.now() - lastEffort.at < 5000 ? ... : null
```

一次请求从决策到收到 `usage` 要 1.3–5.6 秒，长上下文更久。超过 5 秒的请求全部记成
`effort: null` → `avoidedOutputTokens = 0`。实测 31 条记录里只记到 4,593，真值 48,303
（**漏记 90%**），而且漏掉的恰好是慢的、贵的请求——系统性偏差，不是噪声。

修法：撤销 TTL，pre-step 更新 `effortContext` 时清空 `lastEffort`（按轮次失效）。
`verify` 增了源码守卫，防止计时器回来。

**缺陷 2：`costkiller_status` 的 output schema 装不下自己的返回值。**

宿主按 `additionalProperties: false` 校验工具返回值，而 `realBilling / realBillFile /
debugLogFile` 三个字段只出现在返回值里、没写进 schema → 整个工具报
`returned invalid output`。同一个坑还有 `lastPricing`（首个请求前是 `null`）。
修法：补全嵌套 schema、给 `lastPricing` 稳定默认值；`verify` 增了递归的
schema-vs-output 校验，以后不可能只加返回值不加声明。

## 15. 前缀侧两个杠杆的实测（2026-11-11 13:35Z，构建 c35ade3）
